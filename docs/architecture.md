# Архитектура: что происходит в каждом узле

Документ подробно объясняет каждый узел диаграммы из [README](../README.md). Узлы идут в порядке прохождения письма: вход → оркестратор → граф → инструменты → память → обучение.

## Общая картина

Письмо проходит такой путь:

1. Источник письма (CLI или Gmail) передаёт его в `Assistant.process()`.
2. `Assistant` запускает граф LangGraph, у которого два узла: `triage_router` и `response_agent`.
3. `triage_router` решает, что делать с письмом: `ignore`, `notify` или `respond`.
4. Если решение `respond`, `response_agent` пишет ответ и вызывает инструменты. Любая отправка письма останавливается на проверке человеком.
5. Вокруг этого цикла есть три вида долговременной памяти (семантическая, эпизодическая, процедурная). Они делают ассистента лучше со временем без дообучения модели.

Ключевая идея: **поведение ассистента определяется не только кодом, но и данными в хранилище** (store). Правила триажа, инструкции агента, примеры и факты о людях читаются из store при каждом запуске. Поэтому их можно менять во время работы.

## 1. Входные узлы (Input)

Файлы: [cli.py](../src/email_assistant/cli.py), [integrations/google.py](../src/email_assistant/integrations/google.py).

**CLI** (`demo`, `run`, `gmail`, `eval`, `prompts`, `facts`) решает три задачи:

- Берёт письма из `data/sample_emails.jsonl` или из Gmail.
- Показывает пользователю интерактивное ревью черновика: принять, отредактировать, дать обратную связь агенту или проигнорировать. Результат ревью возвращается через `ReviewFn`.
- Предоставляет служебные команды: просмотр и откат версий промптов, поиск фактов, запуск eval.

**Gmail polling** запрашивает непрочитанные письма, приводит их к единому формату `Email` (`id`, `author`, `to`, `subject`, `email_thread`) и передаёт в `Assistant.process()`. Флаг `--watch 60` запускает опрос раз в минуту. Для продакшена в README предлагается заменить опрос на Gmail push через Pub/Sub и webhook.

Оба источника используют один и тот же вход, поэтому остальная система не знает, откуда пришло письмо.

## 2. Assistant — оркестратор сессии

Файл: [assistant.py](../src/email_assistant/assistant.py).

`Assistant` — тонкий слой над графом и тремя видами памяти. Он создаёт граф, держит `store`, `checkpointer`, `user_id` и `PromptRegistry`.

### `process(email, review)`

1. Создаёт уникальный `thread_id` вида `<id письма>-<случайный суффикс>`. Каждое письмо получает отдельный поток, а чекпоинты разных писем не смешиваются.
2. Вызывает `graph.invoke({"email_input": email}, config)`. В `config["configurable"]` лежат `langgraph_user_id` и `thread_id`.
3. Если граф остановился на `interrupt()`, результат содержит `__interrupt__`. Тогда вызывается `review(payload)`, а граф возобновляется командой `Command(resume=decision)`. Цикл повторяется, пока прерываний не останется.

По умолчанию используется `auto_accept`, который принимает любой черновик. Он нужен для тестов и демо. В реальной работе подставляется функция из CLI.

### Методы обучения

| Метод | Вид памяти | Что делает |
|---|---|---|
| `correct_triage(email, label)` | эпизодическая | Сохраняет пару «письмо → верная категория» |
| `give_feedback(state, feedback)` | процедурная | Запускает оптимизатор промптов с гейтом по eval |
| `consolidate_facts(state)` | семантическая | Фоном извлекает и дедуплицирует факты |

Функция `trajectory(state)` превращает состояние графа в читаемую расшифровку сессии: письмо, решение триажа, реплики агента, вызовы инструментов и их результаты. Блоки thinking исключаются. Эту расшифровку получают оптимизатор и экстрактор фактов из LangMem.

## 3. Граф LangGraph

Файл: [graph.py](../src/email_assistant/graph.py).

### Состояние (`State`, [schemas.py](../src/email_assistant/schemas.py))

```python
class State(TypedDict, total=False):
    email_input: Email          # входное письмо
    triage: dict                # {"classification": ..., "reasoning": ...}
    messages: list[AnyMessage]  # диалог агента (редьюсер add_messages)
```

Состояние общее для обоих узлов. Редьюсер `add_messages` дописывает новые сообщения в историю, а не заменяет её.

### Рёбра

```
START → triage_router ──respond──→ response_agent → END
                      └─ignore/notify→ END
```

Единственное ребро `START → triage_router` объявлено явно. Остальные переходы задаёт сам `triage_router` через `Command(goto=...)`, поэтому у узла указано `destinations=("response_agent", END)`.

### Узел `triage_router`

Это классификатор. Он решает, стоит ли тратить на письмо дорогой вызов агента.

**Модель.** Claude с `effort="low"` и `with_structured_output(Router, method="json_schema")`. Нативные structured outputs используются потому, что принудительный `tool_choice` отвергают Opus 5.5, Sonnet 5.5 и Fable 5.1.

**Что происходит, шаг за шагом** (функция `classify`):

1. Читает **процедурную память**. `PromptRegistry.get_all()` возвращает активные версии `triage_ignore`, `triage_notify` и `triage_respond`.
2. Читает **эпизодическую память**. `search_examples()` делает семантический поиск похожих писем, которые пользователь раньше исправил (до 5 штук), и `format_few_shot()` форматирует их в блок промпта.
3. Читает профиль пользователя (`get_profile`): имя и описание роли. Значения по умолчанию лежат в `DEFAULT_PROFILE`.
4. Собирает системный промпт `TRIAGE_SYSTEM_PROMPT` (роль, фон, три категории, правила, few-shot примеры) и пользовательский промпт `TRIAGE_USER_PROMPT` (автор, адресат, тема, тело).
5. Вызывает модель и получает объект `Router` с двумя полями: `reasoning` (рассуждение) и `classification`.

В промпте сказано, что few-shot примеры имеют приоритет над общими правилами. Они отражают реальные предпочтения пользователя.

**Что делает узел с результатом:**

- Записывает `triage = {classification, reasoning}` в состояние.
- Если `respond`, добавляет в `messages` сообщение «Respond to the email: …» и переходит в `response_agent`.
- Если `ignore` или `notify`, сразу идёт в `END`. Агент не вызывается. Сейчас `notify` не отправляет уведомление наружу: результат доступен в `triage` итогового состояния.

Функция `classify` вынесена отдельно, чтобы её можно было вызывать вне графа. Её использует eval-гейт, подставляя через параметр `prompts` кандидатов вместо активных промптов и отключая few-shot через `use_examples=False`.

### Узел `response_agent`

Это ReAct-агент из `create_react_agent`. Он работает в цикле «модель → вызов инструментов → результат → модель» до тех пор, пока модель не перестанет вызывать инструменты.

**Модель.** Claude с `effort="medium"`.

**Системный промпт** собирается динамически функцией `agent_prompt` при каждом шаге цикла:

- Берёт `AGENT_SYSTEM_PROMPT` и подставляет профиль.
- Подставляет `agent_instructions` из процедурной памяти. После `give_feedback` агент сразу начинает писать по-новому.
- Добавляет сообщения из состояния.

**Инструменты:** `write_email`, `schedule_meeting`, `check_calendar_availability` (`BASE_TOOLS`) и `manage_memory` / `search_memory` (`memory_tools()`).

**Типичный сценарий:**

1. Агент ищет в семантической памяти факты об отправителе и теме (так требует промпт).
2. При необходимости проверяет календарь.
3. Пишет ответ через `write_email`. Граф здесь приостанавливается (см. раздел 4).
4. Если узнал что-то постоянное, например «Sarah — руководитель проекта X», сохраняет факт через `manage_memory`.
5. Завершает работу, а граф доходит до `END`.

Язык ответа агент выбирает по языку входящего письма. Это записано в стартовых `agent_instructions`.

## 4. Инструменты агента

Файл: [tools.py](../src/email_assistant/tools.py).

### `write_email` — узел с человеком в контуре

Это единственный инструмент с побочным эффектом, защищённым ревью. Вызов `interrupt()` останавливает граф и сохраняет состояние в checkpointer. Наружу уходит payload `{"action": "write_email", "args": {to, subject, content}}`. Когда `Assistant.process()` возобновляет граф, решение пользователя попадает в код инструмента:

| Решение | Что происходит |
|---|---|
| `accept` | Письмо отправляется как есть через бэкенд |
| `edit` | Поля из `decision["args"]` перекрывают черновик, затем письмо отправляется |
| `response` | Письмо **не** отправляется. Агент получает текст обратной связи и должен переписать черновик и вызвать `write_email` снова |
| `ignore` (любое другое) | Агент получает указание не повторять попытку и завершиться |

Благодаря этому ни одно письмо не уходит без согласия человека. Цикл «черновик → замечание → новый черновик» работает без отдельной логики в графе.

### `schedule_meeting` и `check_calendar_availability`

Они сразу обращаются к бэкенду. `schedule_meeting` принимает участников, тему, длительность, дату (`YYYY-MM-DD`) и время (`HH:MM`). `check_calendar_availability` возвращает свободные слоты на день. Ревью для них нет.

### Backend

Протокол `Backend` (`send_email`, `schedule_meeting`, `availability`) отделяет логику инструментов от реальных систем. Бэкенд выбирается переменной `TOOLS_BACKEND` и кэшируется в `get_backend()`:

- **`mock`** (по умолчанию). `MockBackend` хранит отправленные письма и встречи в списках. Календарь всегда отвечает «9:00, 14:00, 16:00». Это подходит для тестов и демо.
- **`google`**. `GoogleBackend` ходит в Gmail и Google Calendar (OAuth, `credentials.json`, часовой пояс из `TIMEZONE`).

## 5. Долговременная память (Store)

Все ключи лежат в пространствах имён вида `("email_assistant", user_id, ...)`. Это изолирует пользователей друг от друга. `user_id` приходит через `config["configurable"]["langgraph_user_id"]`. Хранилище: `InMemoryStore` по умолчанию или Postgres + pgvector при заданном `DATABASE_URL`.

### 5.1 Семантическая память — факты

Файл: [memory/semantic.py](../src/email_assistant/memory/semantic.py). Пространство: `(app, user, "collection")`.

Это знания о мире пользователя: кто есть кто, предпочтения, договорённости вроде «нет встреч по пятницам».

- **Запись в горячем пути.** Агент сам вызывает `manage_memory` (создание, обновление, удаление по id). Инструкции `MANAGE_INSTRUCTIONS` говорят, когда это делать, и требуют обновлять устаревший факт, а не создавать дубликат.
- **Чтение.** Агент вызывает `search_memory` (семантический поиск).
- **Фоновая консолидация.** `consolidate_facts()` после сессии запускает `create_memory_store_manager` с `enable_inserts` и `enable_deletes`. Менеджер извлекает долговечные факты, склеивает дубли и удаляет опровергнутое. Включается переменной `CONSOLIDATE_FACTS=1`.
- Модель для этой работы: `MEMORY_MODEL` (по умолчанию `claude-haiku-4-5`), потому что LangMem принудительно задаёт `tool_choice`.

### 5.2 Эпизодическая память — примеры

Файл: [memory/episodic.py](../src/email_assistant/memory/episodic.py). Пространство: `(app, user, "examples")`.

Это конкретные случаи: «такое письмо пользователь отнёс к такой категории».

- **Запись.** `Assistant.correct_triage(email, label)` сохраняет письмо, метку, источник и время. Эмбеддинг строится только по полю `text` (`index=["text"]`), а не по метке и метаданным.
- **Чтение.** Перед триажом `search_examples()` ищет до 5 самых похожих писем, `format_few_shot()` превращает их в блоки `FEW_SHOT_TEMPLATE` (тело усекается до 1500 символов).
- **Эффект.** Роутер учится на исправлениях без дообучения. Ошибочная классификация, исправленная один раз, влияет на похожие письма в будущем.

### 5.3 Процедурная память — версионируемые промпты

Файл: [memory/procedural.py](../src/email_assistant/memory/procedural.py). Пространства: `(app, user, "prompts")` и `(app, user, "prompt_versions", name)`.

Четыре промпта: `triage_ignore`, `triage_notify`, `triage_respond`, `agent_instructions`. Их начальные значения лежат в `DEFAULT_PROCEDURAL_PROMPTS`. При первом обращении `_ensure()` создаёт версию 1 со статусом `active`.

`PromptRegistry` хранит для каждого промпта метаданные `{active, latest, history}` и отдельную запись на каждую версию (`prompt`, `source`, `note`, `status`, `created_at`).

Статусы версии: `candidate` → `active` → `inactive` / `rolled_back`, либо `rejected`.

| Метод | Действие |
|---|---|
| `get` / `get_all` | Текст активной версии (читается при каждом запуске) |
| `propose` | Новая версия-кандидат, пока неактивная |
| `activate` | Делает версию активной, старую помечает `inactive`, дописывает в `history` |
| `reject` | Помечает кандидата отклонённым с причиной |
| `rollback` | Возвращает предыдущую активную версию из `history` |

## 6. Цикл обучения процедурной памяти

Это самая сложная часть: `give_feedback` → `optimize_from_feedback`.

1. Пользователь пишет обратную связь, например «такие рассылки не надо присылать мне вообще».
2. `create_multi_prompt_optimizer` из LangMem получает траекторию сессии, обратную связь и четыре текущих промпта. Для каждого указаны подсказка `when_to_update` и инструкция вносить минимальные точечные правки.
3. Изменённые промпты записываются как версии-кандидаты через `propose`. Активная версия не перезаписывается.
4. **Eval-гейт для триажа.** Если изменились триажные промпты, система считает точность на `evals/triage_eval.jsonl`: сначала с текущими промптами (baseline), затем с кандидатами. Кандидаты активируются вместе, только если `candidate_accuracy >= baseline_accuracy + min_delta`. Иначе они получают статус `rejected` с причиной. В оценке участвуют только сами правила, без few-shot примеров (`use_examples=False`), чтобы измерять именно промпт.
5. **`agent_instructions`** автоматической метрики не имеет, поэтому активируются сразу. При неудаче их можно откатить командой `prompts rollback`.
6. Результат возвращается как `OptimizationReport` (что предложено, активировано, отклонено, обе точности).

Без eval-набора кандидаты триажа принимаются без проверки, и откат остаётся возможным.

## 7. Checkpointer

Файл: [config.py](../src/email_assistant/config.py).

Checkpointer сохраняет состояние графа после каждого шага для каждого `thread_id`. Именно он делает возможным `interrupt()`: граф останавливается, процесс может ждать ответа пользователя сколь угодно долго, затем выполнение продолжается с того же места.

- `InMemorySaver` по умолчанию. Состояние живёт, пока работает процесс.
- Postgres при заданном `DATABASE_URL`. Состояние переживает перезапуск.

Не путать со store: checkpointer хранит состояние **одного прогона** (по `thread_id`), а store хранит знания **между прогонами** (по `user_id`).

## 8. Две модели

| Роль | Модель | Причина |
|---|---|---|
| Роутер и агент | `claude-opus-5-5` (`effort` low и medium) | Основная работа. Включены серверные fallback при отказах |
| LangMem (оптимизатор, экстрактор, менеджер фактов) | `MEMORY_MODEL`, по умолчанию `claude-haiku-4-5` | LangMem принудительно задаёт `tool_choice`, а Opus 5.5, Sonnet 5.5 и Fable 5.1 отвечают на это ошибкой 400 |

Эмбеддинги по умолчанию считаются локально (fastembed, многоязычная модель). У Anthropic нет API эмбеддингов, но через `EMBEDDING_MODEL` можно подключить внешний.

## 9. Сводка: кто что читает и пишет

| Узел | Читает | Пишет |
|---|---|---|
| `triage_router` | процедурная (правила триажа), эпизодическая (примеры), профиль | `state.triage`, `state.messages` |
| `response_agent` | процедурная (`agent_instructions`), семантическая (через `search_memory`), профиль | семантическая (через `manage_memory`), `state.messages` |
| `write_email` | решение человека (через `interrupt`) | отправка письма через бэкенд |
| `correct_triage` | | эпизодическая |
| `give_feedback` | процедурная, eval-набор | процедурная (новые версии и активация) |
| `consolidate_facts` | траектория сессии | семантическая |
